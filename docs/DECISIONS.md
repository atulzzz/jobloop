# 关键设计决策

## ADR-001：使用 Electron WebContentsView

**决定：** 使用 Electron 的 `WebContentsView` 嵌入招聘网站。

**原因：**

- 普通 Web iframe 容易受到招聘网站安全策略限制。
- 用户需要应用内登录体验。
- TypeScript 和 React 与现有技术背景匹配。

**代价：**

- 增加桌面应用构建和升级复杂度。
- 需要维护网站兼容性和 Session 安全。

## ADR-002：用户主导浏览器

**决定：** 用户负责登录和主要导航，Agent 在明确触发后读取当前岗位。

**原因：**

- 降低账号安全风险。
- 避免批量爬取和自动操作账号。
- 更符合招聘网站使用边界。

## ADR-003：只支持一个招聘网站

**决定：** 第一版只支持一个目标网站。

**原因：**

- 站点 Adapter 和登录流程差异大。
- 多站点支持不会增加 Agent 核心能力，只会放大兼容成本。

## ADR-004：模型提取事实，代码计算分数

**决定：** LLM 提取岗位和个人事实，确定性代码负责评分计算。

**原因：**

- 模型直接给总分不稳定，也无法解释。
- 分数应可以复现、调权和测试。
- 风评、Gap 友好度等信息缺失时必须显式表达置信度。

## ADR-005：人工审批副作用操作

**决定：** 发送消息、填写、投递和发布等操作必须经过用户确认。

**原因：**

- 招聘账号具有真实业务后果。
- Agent 可能误判页面或参数。
- 面试项目应展示可信任的人机协作边界。

## ADR-006：读取使用三层兜底

**决定：** 信任 Adapter、通用提取、视觉/可访问性兜底依次使用。

**原因：**

- 单站点 DOM 可能变化。
- 模型直接处理完整 HTML 成本高且噪声大。
- 人工纠正可以作为最终兜底。

## ADR-007：Excel 是导入和导出格式

**决定：** 使用数据库作为运行时事实来源。

**原因：**

- 需要状态历史、查询、幂等和并发控制。
- 直接修改 Excel 容易破坏结构并产生难以恢复的错误。

## ADR-008：MCP 只封装适合跨边界的工具

**决定：** 不把所有函数都转换成 MCP 工具。

**原因：**

- 进程内简单函数没有跨进程复用需求。
- MCP 应解决真实的工具发现、调用或跨运行时边界问题。
- 项目重点是理解边界，不是为了协议而增加层级。
